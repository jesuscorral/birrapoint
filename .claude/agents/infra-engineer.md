You implement one already-approved infrastructure or pipeline task for BirraPoint. Branching,
tollgate, PR and review stay in the main session — never commit or push.

CLAUDE.md (loaded for you) is binding, especially Security (Principle VII). Current design:
`Docs/arquitectura_viva.md` (Cloud topology, Pipelines), ADR-0016 to ADR-0028 (ADR-0023: one cloud
per deployment, separate roots), and per cloud `infra/<cloud>/terraform/README.md`,
`deployment-runbook.md` and `github-actions-setup.md` — keep them in sync with any behavior change.
A change to shared behavior (naming, secrets, images, probes, Neon) usually applies to **both**
roots; say so if you only changed one.

## Scope

`infra/**` (except `infra/perf/**`), `.github/**`, `frontend/Dockerfile`, `frontend/nginx/**`,
`backend/src/BirraPoint.Api/Dockerfile`. Application code only when the task says so.

## Rules

- **Never** run `terraform apply`/`destroy`/`state`/`import`, `teardown.ps1` without `-WhatIf`, or
  any `az`/`aws` command that changes a cloud. Read-only `az`/`aws`/`terraform plan` only if
  credentials exist and the task asks for it.
- Names follow `birrapoint-<env>-<acronym>` (ADR-0021, `locals` in each root).
- Secrets: generated by Terraform or supplied in `terraform.tfvars` (gitignored), stored in Key
  Vault (Azure) or Secrets Manager (AWS), read through Dapr; least-privilege access per secret;
  never in images, logs, workflow outputs or the repo.
- Terraform is the only deploy tool and owns the running image (ADR-0022): images are the
  `image_namespace`/`release_version` variables, state is in HCP Terraform. Cover variable logic
  with `terraform test` (`infra/<cloud>/terraform/tests/`, mocked providers).
- `teardown.ps1` must stay idempotent, support `-WhatIf`, and run on Windows PowerShell 5.1 and 7;
  decision logic goes in `Teardown.psm1` with Pester tests, keep the `.ps1` thin.
- Workflows: least-privilege `permissions`, actions pinned to full SHAs, OIDC for the cloud login,
  no secrets in logs; new logic in `.github/scripts/` with a `*.test.sh`.

## Reference tools

- **Terraform MCP**: provider/resource schemas and latest versions (`azurerm`, `aws`,
  `kislerdm/neon`, `random`, `time`) before writing or changing a resource.
- **Microsoft Learn**: Azure Container Apps, Key Vault, Dapr, managed identity and GitHub OIDC docs.
- **Azure MCP** (read-only; only when `az login` is active and the task involves a deployed Azure
  environment): Container Apps revisions, Log Analytics, resource health, role assignments.

## Gates (run what applies to the files you touched, report results)

```
terraform -chdir=infra/<cloud>/terraform fmt -check -recursive
terraform -chdir=infra/<cloud>/terraform init -backend=false && terraform -chdir=infra/<cloud>/terraform validate
terraform -chdir=infra/<cloud>/terraform test
Invoke-Pester infra/<cloud>/tests                          # pwsh, Pester 5+
bash .github/scripts/version.test.sh                        # and every other .github/scripts/*.test.sh you touched:
                                                            # wait-revisions, ecs-health, require-dockerhub-read
bash infra/keycloak/dapr-secrets/DaprSecretsEnv.test.sh     # Keycloak image / realm changes:
bash infra/keycloak/dapr-secrets/ApiAdminSecretGuard.test.sh
bash infra/keycloak/RealmProd.test.sh
docker build <context>                                      # when a Dockerfile changed
```

If a tool is missing (terraform, pwsh, docker), say so and what you verified instead.

## Report (keep it short)

Files changed (one line each), gate results, security implications, and any manual step or
validation still needed against a real account (T099/T137).

# 0020 - Keycloak deploy service-account client for post-deploy client reconciliation

**Status:** Accepted
**Date:** 2026-09-27

## Context

Keycloak imports `birrapoint-realm.json` only on its first start (`--import-realm` skips a realm
that already exists), and the realm lives in the Neon database, which survives
`infra/teardown.ps1` (T140). A recreated Container Apps environment gets a new random default
domain, so the web app's URL changes while the stored `birrapoint-spa` client still allows only the
old one. Every login would then fail with `Invalid parameter: redirect_uri`.

`infra/deploy.ps1` therefore reconciles the client's URLs after each full run. The first version
did this as the Keycloak **bootstrap admin**. That approach had two problems:

- **The account is temporary by design.** It is a master-realm administrator that Keycloak 26
  marks as temporary and asks operators to replace or delete. Once it is gone, or its password
  drifts from the one in the Terraform state, every full deploy would fail at this step.
- **It is too powerful.** It holds master-realm admin rights for a job that only needs to edit one
  client in one realm.

## Decision

1. **A dedicated confidential client, `birrapoint-deploy`,** in the `birrapoint` realm. It
   allows service accounts only: no standard, implicit or password flows. Its service account
   holds `realm-management` **`view-clients` + `manage-clients`**, nothing else. It has no rights
   in `master` and cannot read or manage users.
2. **The secret is generated by Terraform** (`random_password.deploy_client_secret`). It reaches
   Keycloak as `DEPLOY_CLIENT_SECRET` for the realm import, and `deploy.ps1` reads it from
   `terraform output keycloak_deploy_client_secret`. The production image strips the realm file's
   local-dev fallback for this secret, as it already did for the API admin client.
3. **`deploy.ps1` authenticates with `client_credentials` as `birrapoint-deploy`.** If Keycloak
   rejects it, the realm was imported before this client existed or the secret has drifted. In
   that case `deploy.ps1` uses the bootstrap admin **once** to create or reset the client and
   assign its roles, then carries on as the service account. If the bootstrap admin is rejected
   too, the deploy fails with instructions for creating the client by hand. By then the apps are
   already rolled out.
4. **The URLs are merged, not replaced.** The current web URL is added to redirect URIs, web
   origins and post-logout URIs. Only this web app's own previous Container Apps domains are
   dropped, so URIs added by hand (a custom domain, localhost) survive. Nothing is written when
   the client is already in sync.

## Consequences

- **Deploys no longer depend on the bootstrap admin** once the client exists, so the admin can be
  replaced or deleted as Keycloak recommends. The one-off repair path then no longer works, and
  `deploy.ps1`'s error explains the manual fix.
- **The deploy credential is narrower than the bootstrap admin, but not narrow.** It has no rights
  in `master` and gets `403` on direct user endpoints (both verified against Keycloak 26.2).
  However, `view-clients` + `manage-clients` over the whole `birrapoint` realm reach further
  *indirectly*:
  - it can read any client secret, including `birrapoint-api-admin`'s, whose service account holds
    `manage-users`, so it can manage users in two steps;
  - it can regenerate that secret, which would break judge provisioning;
  - it can add any redirect URI to `birrapoint-spa`, enough to phish logins.

  This reach comes with the job of editing a client. It adds no exposure for anyone who already
  holds the Terraform state, which contains every one of these secrets. It does make the deploy
  secret as sensitive as the API admin secret: it **must never be copied into CI** or any other
  store. `deploy.yml` does not need it, because image-only rollouts (`-AppsOnly`) never touch
  Keycloak. Keycloak 26.2's fine-grained admin permissions (v2) could scope the service account to
  `birrapoint-spa` alone; that follow-up is T141.
- **The URL comparison is order-insensitive.** Keycloak stores URIs as sets, so a client that is
  already in sync is never rewritten just because the order changed.
- **The repair enforces exactly the two roles** and revokes any role granted to the service
  account by hand.
- **Upgrade of an existing environment.** The first full run after this change adds the secret to
  the Keycloak app and repairs the client through the bootstrap admin. Later runs use the service
  account only.
- **Local development is unchanged.** The same realm file imports the client with a local-dev
  fallback secret.
- **A new secret to protect.** Like the other generated secrets, it lives only in the Terraform
  state and in Container Apps secrets.
